# 实验与分析记录（deepseek-v4-pro，SWE-bench Verified 50 题子集）

> 第 1–3 节：第一次（联网）baseline 的 9 个失败题与泄漏发现；第 4 节：改进 B（自检）；第 5 节：改进 B2（独立审查）。
> 方法：对比模型补丁 / 官方补丁 / 隐藏测试报错 / 完整轨迹。7 题由子 Agent 初筛后我抽查，2 题（django-11087、11734）+ astropy-13398 由我直接分析。

| django-15957 | SPEC_MISREAD | WEAK_VERIFICATION | 第 32 步注意到输出与 issue 期望（每类各取几条）矛盾，自我说服后忽略 |

## 2. 关键模式

1. **定位不是瓶颈**：9 题全部改对了文件/函数。→ 候选 C（代码检索工具）缺乏依据。
2. **"看到了证据却合理化掉"**（12273、15957、6461，3993 也类似）：模型自己的输出或推理已经指出问题，但它为了"最小改动""别复杂化"放弃。→ 支持候选 B：先从 issue 写出**验收标准**，提交前逐条对照自检。
3. **验证只测"不报错"，不测"结果对"**（11734、6461）：→ 同样落在 B 的自检里（要求写出预期值再运行）。
4. 2 题含 TEST_ARTIFACT，属于难以通过 Agent 设计解决的部分，作为"上限"如实报告。

## 3. 重大发现：Agent 联网获取上游修复（数据泄漏）

容器默认有网络。50 题中 **16 题**有联网命令（pip download 新版本、curl GitHub raw、GitHub API 搜索）：

- **sympy-23950**：下载 sympy master 的 `contains.py`，其中正是修复 `return self.args[1]`，照抄后通过。
- **django-11433**：用 GitHub API 搜索，搜到了他人上传的 "[RD-Bench V2] Fix: django__django-11433" 解答仓库。
- django-12273、15098、11095、14725 等下载了更新版本的 Django 源码作对照。

联网的 16 题通过 11 题，未联网的 34 题通过 30 题（联网多发生在难题上，不能直接说明影响大小）。

**结论**：82% 被网络访问污染，不能作为基线。需在 `--network none` 下重跑；之后所有实验统一断网。

## 4. 断网 baseline（78.0%）与改进 B（self_check）的结果

| | 断网 baseline | B：提交前自检 |
|---|---|---|
| resolve | 39/50 = 78.0% | 39/50 = 78.0% |
| 平均步数 | 50.6 | 58.2（自检前 52.0 + 自检 6.2） |
| prompt tok / 题 | 1.93M | 2.51M（自检前 2.16M + 自检 0.34M） |

**结论：B 是负结果，自检基本是"橡皮图章"。**

- 自检只在 **3/50** 题中改动了补丁，这 3 题的通过情况都没变。
- 与 baseline 相比翻转的 4 题（11087、6461 由过变不过，11734、3993 由不过变过）在自检时**补丁都没动**，翻转来自自检之前那段轨迹的随机性。
  → 这给出了**噪声下限**：同配置重跑，约 4/50（8%）的题会翻转，净差 ±2 题以内都不可信。
- 自检本身成本约 +0.34M tok/题（+18%）；其余差额（2.16M vs 1.93M）同样是随机波动。

**为什么没用（看两道失败题的自检过程）**：
- **django-15957**：自检中模型**自己想到了正确做法**（Window + RowNumber，正是官方补丁），判断"太复杂、不太可能"后放弃；随后写的 EXPECTED 值直接照抄现有（错误）行为 `c2: []`，于是"全部通过"。
- **django-12273**：把验收标准收窄成 issue 里的字面例子（`uid = None`），自然全部通过。
- 共性：**同一个模型、带着同一段上下文自检，会继承原有的理解偏差**，预期值被写成"和我现在的实现一致"。

**下一步候选**：
- **B2：独立审查者**。用新的上下文，只给 issue + diff（不给原轨迹），先独立写出预期行为，再判断补丁是否满足；不满足就把意见返给主 Agent。对应"生成者-验证者分离"。
- **B3：先写验收标准再写代码**。在看代码之前就让模型把预期行为写死，避免事后迁就实现。

## 5. 改进 B2（独立审查者）的结果

**总分 42/50 = 84.0%，但审查本身的贡献为 0。**
方法：把被驳回的 5 题的**第一次提交**也送去评测，得到"同一次运行、没有审查"的反事实分数——同样是 42/50。
→ 84% 与断网 baseline 78% 的差距来自主 Agent 轨迹的随机性，不是审查带来的。（这个"评测首次提交"的做法不用重跑就能剥离噪声，后续改进都该这么评。）

| 审查者表现 | 数值 |
|---|---|
| 驳回 | 5/50，其中**正确驳回 2**（13398、15098，都是已有测试回归），**误驳回 3**（11292、13496、15957） |
| 召回 | 第一次提交失败的 8 题中只驳回了 2 题 |
| 无结论 | **9/50 题审查者用满 40 步没给结论**，按设计自动放行（其中 2 题本来是错的） |
| 成本 | 审查者 0.39M tok/题，占总量 15%（新上下文短，比自检便宜：自检是在 2M+ 的长上下文上追加） |

**驳回之后**：
- 2 次正确驳回 → 主 Agent 都**没能修好**（两题本身很难：astropy 功能提案、django i18n 回归）。
- 3 次误驳回 → 主 Agent 复现检查后作出调整，**没有把任何正确补丁改坏**（"审查者可能出错，自己复现再决定"这句提示起了作用）。
  - 13496：审查者要求"补测试"，与主任务"不要改测试文件"的约束冲突；
  - 15957：审查者指出"先取全部行再在 Python 里切片，不够高效"，这点其实合理，但隐藏测试没要求。

**漏掉的失败（PASS 但其实错）**：12273、12325、25479、23950。12273 审查者只用了 12 步就放行——和主 Agent 犯了**同样的理解偏差**（只验证 issue 里的字面例子）。

**结论**：
1. 上下文独立 ≠ 判断独立：**同一个模型当审查者，会和生成者犯相关的错误**，理解偏差类失败（本子集的主要失败类型）几乎抓不到。
2. 审查者能抓到的是"已有测试回归"这种有硬证据的问题，但这类题主 Agent 拿到反馈也修不好。
3. 正面结论：在审查者 60% 误报的情况下，主 Agent 没有被带偏（0 个正确补丁被改坏）——机制是安全的，只是没有收益。

## 6. 离线验证者基准与候选选择（C）

**动机**：B/B2 的问题是"驳回后重做"，而重做修不好难题。但三次断网运行合起来 pass@3 = 44/50，比单次（39–42）高出约 5 题——模型**能**写出正确补丁，只是不稳定。所以改问：能不能从已有候选里**挑出**对的那个？这件事可以完全离线做，不用重跑 Agent。

**数据集**（`scripts/verifier_data.py` → `runs/verifier/patches.jsonl`）：把 5 次运行（含联网 baseline、review 的首次提交）的补丁按实例去重（忽略 `index` 行和行尾空白），得到 **156 个不同补丁 / 50 题，118 对 38 错**，标签来自隐藏测试。完全相同的补丁在不同运行中的标签**0 冲突**，说明评测是确定的。

**被评估的验证者**（`configs/judge.yaml`，`scripts/judge.py`，都只给 issue + diff，单次调用、无工具）：
- **Pointwise**：给单个补丁打 0–100 分（"通过隐藏测试的概率"）。
- **Listwise**：把同一题的所有候选（随机顺序）一起给模型，选最可能对的一个；每题 3 种顺序。

### 6.1 Pointwise：看起来有用，其实只是在判断"题难不难"

| 指标（low effort，152 个有效分数） | 值 |
|---|---|
| AUROC（全部补丁） | 0.735 |
| **AUROC：每个补丁直接用"它所在题目的平均分"代替** | **0.740** |
| **题内 AUROC：同一题的对补丁 vs 错补丁（33 对）** | **0.424** |

用题目平均分（完全不看具体补丁）就能达到同样的 AUROC → 全局 AUROC 完全来自**题目难度**：judge 能看出"这道题难、补丁多半不对"，但在**同一道题的几个候选之间排序时比随机还差**。
默认推理强度跑完的 57 个补丁上结论相同：全局 0.830，题目平均分 0.868，题内 0.400（只有 5 对）。
→ **方法论结论：评估用于选择/重排的验证者时，全局 AUROC 有误导性，必须看题内指标。**

逐题看：pointwise 能抓住"明显错"的补丁（django-11734 错补丁 0 分；xarray-3993 缺 deprecation 的补丁 25 分，正是第 1 节归因的问题），但对"看起来对、细节错"的补丁，对错候选都给 80–95 分，排序由噪声决定。

### 6.2 选择结果（候选池 = 3 次断网运行在 reviewer 介入前的补丁）

只有 8 题的候选有对有错，其余 42 题无论怎么选结果都一样。

| 选择方式 | 50 题解出 | 8 道"有对有错"题 |
|---|---|---|
| 随机挑一个（= 期望 pass@1） | 40.0 | 4.0 |
| 多数投票（补丁去重后谁出现最多） | 40.0 | 4.0（3 个候选全不同，退化为随机） |
| Pointwise 取最高分 | 39.5 | 3.5 |
| **Listwise（单次调用）** | **41.3** | **5.3** |
| Oracle（pass@3） | 44.0 | 8.0 |

Listwise 23 次有效调用中 15 次选对（随机期望 11.3），单侧 p = 0.08（Poisson-binomial 精确检验）——**方向正面，但 8 题的样本不足以显著**。

- 稳定选对：django-15957（3/3）、11734、sphinx-8548。15957 的理由正中要害："要求每个分类各取 3 条，候选 1/3 仍在全局 LIMIT"——这正是第 1 节中主 Agent 自己注意到、却合理化掉的那个矛盾；而 pointwise 给这道题的正确补丁打了三者中最低的 75 分。
- 选错：seaborn-3187（0/3）、xarray-6461、pylint-6528（各 1/3）。

**结论**：
1. **对比比打分有效**：把候选放在一起，模型能定位"候选之间行为上的差异"再对照 issue 判断；单独打分时，它对每个看起来合理的补丁都给高分。
2. 这是本项目第一个正向信号（+1.3 题 / 50，在 8 道可改进题上 4.0 → 5.3），但仍是 oracle 上限（+4）的约 1/3，且统计上未显著。
3. 成本：listwise 只需在候选不一致时调用（本例 8/50 题），每次一个调用；相比 B/B2 每题 +0.34M~0.39M token 便宜得多。真实系统中需要先跑 N 次 Agent，这才是主要成本（N=3 约 3× 生成成本）。
